# Decisions

Accepted by the owner (Mike Zupper) on 2026-10-19 unless noted. Changing one is an escalation.

| # | Decision | Why |
| --- | --- | --- |
| D1 | **Streaming is a requirement**, and the design must be generic to builder-core, not specific to ChatLPT. | Other apps on the engine need incremental text and media. |
| D2 | Pin `livepeer-builder` to the streaming branch `tasks/m3/mz/stream-support` (off `releases/m3`) at commit `93756ba`, as a git reference (moved 2026-10-21 from `a89216d` to take the PR #28 review fixes, builder-core D40; on 2026-10-20 from `973ac57` to take the stream lifecycle fixes, D34–D39). Re-pin to the merge commit, then to a release tag, once reviewed. Before 19 October the pin was the `v0.1.0` tag (the M2 close-out). | The app needs `jobs.stream`; the branch is the reviewed baseline-to-be. |
| D3 | **One shared application payment key** (`per_application` mode). The app tracks per-user input and output tokens (retail) and the engine's per-job network cost (wholesale). Both are kept. | Enterprise pays the network once; the app owns customer accounting. |
| D4 | **Retail prices come from Alibaba Cloud's list prices for Qwen3.8-27B**, international (Singapore) region, in USD, with input, cached input, output and thinking-mode output priced separately. The table is a dated file in the repository with its source URL. | A "hypothetical" cost like ChatGPT's needs a public, defensible rate. |
| D5 | **Email and password accounts** in SQLite, **self-signup open**. No magic links. | Simplest credible enterprise login for a sample. |
| D6 | **Google and GitHub sign-in** when configured (authorization code with PKCE). Linking by email follows D26. | Common enterprise identity providers; one library handles both. |
| D7 | ~~Admins are the emails in `CHATLPT_ADMIN_EMAILS`.~~ **Superseded by D26 (2026-10-20):** anyone who signed up first with a listed email became admin. | — |
| D8 | Orchestrators: `https://orch-us-central.xodeapp.xyz:18935`, `https://us-central-metrics.speedybird.xyz:28935`, `https://orch-eu-central.open-pool.com:443`, `https://hky.eliteencoder.net:8936`, and, added 2026-10-19 for image generation, `https://ai1.eliteencoder.net:8936` (73 fal apps including `comfystream/fal-flux-schnell`). The engine's discovery is filtered to the approved apps on these hosts. | The first four run `blueclaw/chat/qwen3.8-27b` (evidence in builder-core, 14 and 19 October); ai1 is the only known host of FLUX schnell. |
| D9 | **Rebuild** the Clearinghouse Batteries and node signer images from the pinned commits (`ca09e47`, `406b248`) in `scripts/build-images.sh`. Never push from the script. | Reproducible stack; same pins as builder-core's dev-stack. |
| D10 | **Run the full payment stack in dev** from this repository's compose file, reading the payer keystore from `~/.livepeer/keys/cloud-spe-gateway`. Do not point at another running signer. One signer per payer account at a time. | Two signers on one keystore is asking for trouble. |
| D11 | **SQLite** for both the app database and the embedded engine's database, on one volume. | One container, no database service, enough for a sample. |
| D12 | Harness-engineering approach: AGENTS.md as a map, `docs/` as the system of record, structural tests, exec plans. **No beads.** **No attribution trailers** in commits or PRs. Commit as you go; never push without review. | Owner preference; matches builder-core. |
| D13 | **No GitHub CI in v1.** Checks run locally and are listed in AGENTS.md. | Scope; v2. |
| D14 | **The context window is derived**, not configured. Order: the runner's discovery `metadata` (`max_context`, `model_id`; free; the **smallest** value across the approved runners, since the engine may route to any of them: 40960 on speedybird, 131072 on xode and hky on 2026-10-19), then the cached value, then `GET /v1/models` (`max_model_len`, a paid call), then a stale cache, then `CHATLPT_CONTEXT_WINDOW_OVERRIDE`, then 8192. History is truncated to fit it minus the output reserve. | The model on the network knows its own limits; the metadata costs nothing. |
| D15 | Show the model's **reasoning** in a collapsible block when present; reasoning tokens are billed as output in retail. | Matches ChatGPT; matches how Alibaba bills. |
| D16 | Conversation titles come from the first user message. No extra paid call. | Every call spends money. |
| D17 | A minimal **admin page** shows per-user retail vs network totals (delivered and failed, D29) and the margin. | The margin is the point of the demo. |
| D18 | The public base URL and port are settings (`CHATLPT_PUBLIC_BASE_URL`, default `http://localhost:3050`). | OAuth callbacks need it; no preference yet. |
| D19 | Token counts come from the runner's `usage` with `stream_options.include_usage`; the app also reports them to the engine with `report_usage`, so both books share the job id. | One source of truth for tokens. |
| D20 | The ChatLPT engine adapter is **streaming-shaped from day one**. The v0.1.0 implementation yields the whole reply as one chunk; the streaming implementation yields deltas. Only `adapters/engine.py` changes. | Nothing in the app is written twice. |
| D21 | Order of work: scaffold ChatLPT end to end against v0.1.0 first (proves payments, auth, billing), write the builder-core streaming exec plan in parallel, then build the branch, then swap the adapter. | Validate the most things with the least new code. |
| D22 | MIT license; the repository lives under the NE-Build-Track organization. | Matches builder-core. |
| D24 | **Continue generating, and a thinking level per conversation** (2026-10-19). A reply cut off at `length` can be continued: the partial answer goes back as the final assistant turn with vLLM's `continue_final_message`, and the result is a new assistant segment (`continues_message_id`) so each paid job keeps its own ledger row; the model sees the chain as one turn. Each conversation has a thinking level, off / low / medium / high, mapped to `enable_thinking`, a chain-of-thought budget (1,024 / 4,096 / 16,384) and `reasoning_effort`; default medium. A reply records how many earlier turns were left out of the context (`dropped_turns`) and the UI says so. | This is how hosted assistants behave: large limits, continuation on truncation, a reasoning setting, and honesty about what the model could not see. |
| D25 | **Images are model-driven only** (2026-10-19): the assistant is offered a `generate_image` tool and decides when to draw, the app runs `comfystream/fal-flux-schnell` through the engine, stores the image on the volume, feeds the tool result back and the model writes the caption. No explicit image button. Tools are offered with at least low thinking because the tool decision was unreliable with thinking off. Retail for an image is fal's list price per megapixel rounded up (`config/pricing/fal-flux-schnell.json`). | This is ChatGPT's native behavior; verified live ([evidence](../references/evidence/2026-10-19-model-driven-images.md)). |
| D23 | **Output limit 32,768 tokens** (`CHATLPT_MAX_OUTPUT_TOKENS`; 16,384 at first), and a reply whose `finish_reason` is `length` is shown as cut off, never as blank. Added 2026-10-19 after a reply spent all 2,048 tokens thinking. | Qwen's chain of thought counts against `max_tokens`; the network bills per second, so a tight token cap only loses answers. This is how hosted assistants behave: large output limits, a separate reasoning budget, truncation shown as such. |
| D26 | **A verified email wins** (2026-10-20, from the review of ChatLPT). A password signup is unverified; an account created or linked by Google or GitHub is verified (`users.email_verified`). A provider sign-in links automatically only into a verified account. When it proves an email that an **unverified** password account uses, the person chooses once (a signed cookie holds the proven identity for 10 minutes): enter that account's password to keep it and its history (it becomes verified), or continue with a new account, which **claims** the address: the old account is disabled, its password deleted, its email renamed to `unclaimed+<id>@invalid`, its data kept with it for admins; its open sessions end on the next request. Claims work even when signup is closed. **Admin rights come only from `chatlpt make-admin EMAIL`** (refuses an unverified account without `--allow-unverified`) and `revoke-admin`; `CHATLPT_ADMIN_EMAILS` is gone, and a claim retires an unverified admin too. Login, signup and the claim prompt allow 5 attempts a minute per email and 20 per client address (`CHATLPT_TRUST_FORWARDED_FOR` behind a proxy). Emails match exactly after lower-casing. Signup stays open by default (D5). | Signup proves nothing about an email; a provider does. Before this, a stranger could sign up with your address, wait for you to sign in with Google, and share your account; or sign up first with an admin address. |
| D27 | **OAuth fails on the login page, not in the browser** (2026-10-20). Every callback failure (cancel at the provider, an expired or foreign `state`, no verified email, a disabled account, closed signup, a provider or network error) redirects to `/login?error=<reason>` with a plain message and logs `auth.oauth_failed`. The flow uses PKCE (S256; the verifier rides in the signed state cookie). No `id_token` is used, so no nonce is sent. `next` must be a path on this site (backslashes and control characters refused). With a provider configured, the app refuses to start unless `CHATLPT_PUBLIC_BASE_URL` is `https` (or `http` on localhost), and logs the exact redirect URIs to register. | The first real sign-in test would otherwise meet raw JSON, 500s and `redirect_uri_mismatch`. |
| D28 | **A fresh start for the database** (2026-10-20). ChatLPT has no data worth keeping, so the four migrations were folded into one baseline `0001`, and deployments recreate the `chatlpt-data` volume. Later changes add migrations on top. | No backward compatibility to carry for a sample that is a day old. |
| D29 | **The network book is read from the engine, never copied** (2026-10-20). The embedded engine already keeps the Batteries usage rows and a cost per job in its own database in this container. ChatLPT shows a message's or image's network cost from `engine.costs.for_job` each time it is read, and a user's totals from `engine.costs.summary`, split into delivered spend and failed spend (failed after payment plus uncertain), with pending jobs counted beside them. ChatLPT stores no network cost: the `wholesale` columns and the background poller are gone. A failed paid reply keeps its engine `job_id`, so its cost shows and counts. The engine's `none` means no attempt was paid: a settled $0 (a warning is logged if the app believed the job paid). A job the engine has no record of is `unknown`, never $0. The admin page shows failed network spend in its own column, and the margin subtracts it. Retail stays in the app's ledger (D3, D4). | A second copy needed a poller that could stall behind costs that never settle, left failed paid replies out of the books, and read `none` as "not yet known". The engine is the source of truth for network cost. |
